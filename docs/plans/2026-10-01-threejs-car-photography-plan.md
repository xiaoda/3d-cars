## 一、项目定位与目标

将项目定位为以 Three.js 为核心的“汽车虚拟摄影棚”，而不是大型驾驶游戏。

面向宝马、奔驰、奥迪、雷克萨斯等量产豪华车型，支持在不同场景、车辆状态和摄影角度下制作高清照片及短视频。

### 1.1 核心使用流程

选择车型 → 选择场景 → 调整车漆与车辆状态 → 选择摄影机位 → 实时预览 → 高质量渲染 → 保存作品。

### 1.2 优先级

1. 车辆比例、曲面、细节与材质的真实感。
2. 灯光、反射、构图和最终成片质量。
3. 高清照片导出的稳定性与可复现性。
4. 实时预览的交互体验。
5. 短视频、更多车型及复杂环境。

不要先制作一个功能齐全、但车辆始终不够真实的编辑器。模型、材质与灯光是视觉质量的基础，增加 UI 功能不能弥补这些问题。

| 项目 | 计划目标，尚未实测 |
|---|---|
| 实时预览 | 1080p，争取稳定约 30 fps，支持降低预览分辨率 |

### 2.2 针对当前电脑的约束

- 开发时确认浏览器实际使用 RTX 3060。检测到独显，不代表网页已经使用独显。
- 预览与最终出片按需切换资产，避免两套高精度资源长期同时驻留。
- 显存占用需要包含几何、贴图、反射资源、渲染目标和路径追踪加速结构，不能只看 GLB 文件大小。
- 每次视频导出前检查磁盘空间，限制临时文件规模，提供明确的清理入口。
- 第一阶段测量预览帧率、显存占用和单张渲染耗时，再确定正式画质档位。
- 目前不承诺具体的单张照片或视频渲染速度。

## 三、渲染路线选择

| 路线 | 优点 | 代价与限制 | 建议 |
|---|---|---|---|
| 全程 Three.js 实时渲染 | 交互直接，导出快 | 复杂反射、玻璃与间接光需要近似处理 | 作为实时预览基础 |
| Three.js 实时预览＋路径追踪出片 | 保持浏览器工作流，静态画质潜力更高 | 需要等待采样，存在材质兼容和视频噪点问题 | 一期主路线 |
| Three.js 编辑＋Blender 最终渲染 | 可进一步追求高质量成片 | 两套材质、灯光与场景同步更复杂 | 后续可选扩展 |

### 3.1 推荐方案

- **预览模式**：Three.js `WebGLRenderer`，用于旋转车辆、调整灯光和构图。
- **照片模式**：先验证 `three-gpu-pathtracer`，停止交互后累积采样，再导出高清图片。
- **视频模式**：先实现逐帧渲染与编码，再评估路径追踪视频的耗时和时间连续性。
- **可选离线模式**：如果浏览器路线无法满足目标画质，后续评估 Blender 最终出片，不在一期同时实现两套完整管线。

`three-gpu-pathtracer` 是基于 WebGL 2 的第三方项目，不是 Three.js 官方内置渲染器。它存在材质、几何和灯光支持限制，不能假设所有实时效果都能直接进入最终出片管线。[项目文档](https://github.com/gkjohnson/three-gpu-pathtracer)

一期不建议同时引入 WebGPU。它可以作为后续技术分支，但材质、后处理和渲染器迁移需要单独验证；更换图形 API 本身并不等于获得照片级效果。[Three.js WebGPURenderer 文档](https://threejs.org/manual/pages/webgpurenderer)

### 3.2 首轮技术验证内容

1. 同一车型在实时渲染与路径追踪中的材质表现。
2. 车漆、玻璃、灯罩、环境反射与地面效果的兼容性。
3. 当前电脑上的初始化耗时、采样耗时和资源占用。
4. 相机或车辆变化后，场景更新及采样重置是否正确。
5. 保存图片与预览画面的色彩是否一致。

如果验证失败，应明确调整模型、材质或渲染路线，不能用低质量占位效果冒充最终方案。

## 四、真实车型资产策略

### 4.1 不用程序化模型承担最终车身

程序化建模适合占位车、道路、建筑和背景道具，不适合承担真实品牌车型的最终精细车身。

真实车型容易露馅的地方包括：

- 车身比例、轴距、轮径与姿态。
- 引擎盖、翼子板、车门的连续曲面。
- 大灯内部结构、格栅、轮毂和刹车。
- 车窗厚度、内饰遮挡与钣金接缝。

优先选购或取得有明确授权的高质量模型，用 Blender 整理后转换为浏览器资产。不将来源不明的游戏提取模型作为项目基础。

### 4.2 首车只选一辆

候选方向包括宝马 3 系、奔驰 C 级、奥迪 A4、雷克萨斯 ES 等，最终要明确年款与配置。

选择顺序：模型质量与授权适配 → 可编辑程度 → 个人车型偏好 → 品牌覆盖数量。

### 4.3 模型采购与验收清单

| 检查项 | 要求 |
|---|---|
| 外观准确性 | 对照实车参考图，不只看卖家的精修渲染图 |
| 部件拆分 | 车身、车窗、车灯、轮胎、轮毂独立 |
| 活动部件 | 开门或转向需要独立部件及正确转轴 |
| 内饰 | 外观摄影至少需要车窗后有合理结构 |
| 材质 | 有可整理的 PBR 贴图和明确材质槽 |
| 源文件 | 尽量保留可编辑原始资产，不只保留压缩 GLB |
| 授权 | 核实成片使用、商业用途及网页分发限制 |

“渲染成图片或视频”与“把模型放进公开网页供浏览器下载”是不同使用方式。模型采购前需核对具体条款；付费购买不代表获得任意用途授权。CGTrader 的 Editorial 模型和模型再分发就有专门限制。[CGTrader 授权条款](https://www.cgtrader.com/pages/terms-and-conditions)

### 4.4 固定资产处理流程

```text
授权模型
  ↓
Blender 清理与校准
  ├─ 尺寸、坐标、法线
  ├─ 材质槽与贴图
  ├─ 部件命名、转轴、动画
  └─ 对照参考图检查
  ↓
预览资产＋高质量出片资产
  ↓
车型配置与能力清单
```

每辆车声明自身支持的功能，例如转向、开灯或开门。没有对应结构的模型不显示该功能，不承诺所有车型都能任意操作。

## 六、场景建设顺序

### 6.1 摄影棚：首个场景

用于检查车身曲面、车漆和反射。先建立可控的背景、地面、主光与轮廓光，再调整摄影机位。

### 6.2 黄昏室外平台

检验车辆与真实环境的融合，重点处理天空、地面、环境光、主光方向及接地关系。

### 6.3 地下停车场

突出顶灯反射、轮廓光和车灯效果。先建设足够拍摄的局部空间，不搭建整座停车场。

### 6.4 后续雨夜场景

在基础效果稳定后，再增加湿地面、水滴、雾和动态降雨；分别验证照片与视频表现。

### 6.5 环境资产原则

HDRI 可以提供环境光与远景，但不能代替所有三维环境。镜头绕车或跟车时，近处道路、墙面、立柱需要真实几何，否则视差、遮挡与反射容易穿帮。

HDRI、地面材质等可优先筛选 Poly Haven 的 CC0 资产。[Poly Haven 授权说明](https://polyhaven.com/license)

## 七、真实感的重点投入

### 7.1 车漆

- 区分底层颜色、粗糙度和表面清漆。
- 普通漆、金属漆、珠光漆不只靠更换颜色值区分。
- 一期先用标准物理材质建立可靠基线。
- 金属闪粉等自定义效果后置，分别验证实时与路径追踪支持情况。

Three.js 的 `MeshPhysicalMaterial` 提供清漆、透射等属性，但复杂功能会增加渲染成本。[官方材质文档](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)

### 7.2 反射与灯光

汽车大量形体信息来自反射，应重点设计摄影棚的长条柔光与明暗反射区域、环境光和主光方向、车轮接地阴影、车身与近处环境的反射关系。

预览可以采用环境贴图、局部反射探针或针对地面的平面反射；最终出片使用更准确的渲染方式。不要指望一个屏幕空间反射效果解决所有情况。

### 7.3 玻璃与车灯

- 玻璃不仅要透明，还要有合理的反射、透射和内部结构。
- 车灯不能只是白色发光块，需要灯罩、内部结构及实际照明。
- Bloom 只作为点缀，不能通过过曝掩盖细节。

### 7.4 摄影与色彩

摄影预设不仅保存相机坐标，还应保存焦距、目标点、曝光、对焦距离、景深、画幅和灯光配置。

尽早固定色彩流程，统一贴图颜色标注、线性工作空间与最终输出转换，避免预览、图片和视频明显偏色。[Three.js 色彩管理文档](https://threejs.org/manual/pages/color-management.html)

## 八、工程架构与技术栈

### 8.1 推荐技术组合

| 部分 | 建议 |
|---|---|
| 编辑器界面 | React＋TypeScript＋Vite |
| 三维核心 | Three.js，独立于界面组件 |
| 最终照片 | `three-gpu-pathtracer`，先验证后接入 |
| 模型整理 | Blender |
| 状态与配置 | 轻量状态管理＋带版本的 JSON |
| 本地导出助手 | Node.js |
| 视频编码 | 本机 FFmpeg |
| 数据存储 | 一期使用本地文件，不急着上数据库 |

### 8.2 模块关系

```text
编辑器界面
    ↓
拍摄项目配置
    ├─ 车型与车辆状态
    ├─ 场景、灯光与材质
    ├─ 相机与时间轴
    └─ 输出参数
    ↓
Three.js 场景构建
    ├─ 实时预览
    └─ 高质量渲染
             ↓
        图片 / 帧序列
             ↓
        FFmpeg 视频编码
```

### 8.3 关键架构决策

| 决策 | 原因 | 代价或边界 |
|---|---|---|
| 实时预览与最终出片分离 | 交互速度与最终画质不必互相牺牲 | 需要维护兼容性和画面差异检查 |
| 三维核心与 React 界面解耦 | 便于独立渲染、测试和批量导出 | 初期需要明确场景操作接口 |
| 资产与摄影配置分离 | 同一车型可以复用到多个作品 | 需要管理资产版本与引用关系 |
| 本地优先、单应用结构 | 降低部署与运营复杂度 | 一期不覆盖多人协作与远程算力 |

### 8.4 配置可复现

保存的是“拍摄配方”，而不是只有截图。至少包括：

- 配置格式版本与资产版本。
- 车型、车辆状态、材质参数。
- 场景、灯光、相机参数。
- 时间轴、随机种子。
- 输出尺寸、帧率与渲染设置。

渲染核心应能独立加载项目、设置时间和输出画面，方便自动测试与批量导出。

### 8.5 本地运行与安全边界

- 本地服务仅监听 `127.0.0.1`，限定资产与输出目录。
- 不将用户主目录、凭据目录或无关文件暴露为静态资源。
- 文件路径和输出参数需校验，导出不能任意覆盖无关文件。
- 辅助服务后台执行，记录日志、PID、工作目录和实际端口。
- 不默认弹出终端窗口，不抢占用户焦点，不全局结束浏览器或共享进程。
- 只清理本任务创建且不再需要的进程与临时文件。

## 九、视频与图片导出设计

### 9.1 视频使用逐帧渲染，不依赖录屏

```text
设置第 i 帧时间：t = i / fps
    ↓
更新相机、车辆、车轮、灯光
    ↓
等待场景更新完成
    ↓
渲染到指定画质
    ↓
保存该帧
    ↓
下一帧
    ↓
FFmpeg 合成视频
```

FFmpeg 支持按指定输入帧率读取编号图片序列并生成视频。[FFmpeg 文档](https://ffmpeg.org/ffmpeg-formats.html#image2)

这种方式允许每帧渲染慢于实际播放速度，同时保持正确的成片时长与帧数。

### 9.2 必须处理的问题

- 路径追踪在每帧变化后重新累积，可能产生噪点闪烁。
- 运动模糊需要专门设计，不会因为车轮开始旋转就自动具备。
- 动画按固定时间求值，不依赖浏览器实际运行帧率。
- 帧文件逐步写入磁盘，不将整段高分辨率视频全部保存在内存。
- 中断后保留已完成帧，记录任务配置和进度，支持继续任务。
- 编码失败与渲染失败分开报告，避免因为编码失败丢弃可用帧。
- 图片和视频输出需要验证尺寸、颜色、完整性与可打开性。

### 9.3 耗时估算方法

总帧数 = 视频时长 × 帧率。

预计总耗时 ≈ 总帧数 × 实测平均单帧耗时，再加场景准备、磁盘写入和编码时间。

例如，10 秒、30 fps 是 300 帧。如果每帧需要 5 秒，纯渲染约需 25 分钟。这只是计算示例，不是对当前电脑的实测结论。

## 十、开发阶段与验收

下列工作量以已有合适模型、具备相关开发经验为前提，不包括从零制作精细车型。实际工期在 P0 技术与画质验证后调整。

| 阶段 | 主要工作 | 验收结果 | 粗略工作量 |
|---|---|---|---|
| P0：画质验证 | 选首车、整理模型、搭摄影棚、比较渲染路线、测量硬件表现 | 一张认可的目标效果图和基本性能记录 | 3–5 天 |
| P1：单车摄影 | 车辆加载、材质、灯光、机位、图片导出 | 稳定拍出不同角度的高清图 | 1–2 周 |
| P2：场景与编辑 | 三个场景、状态控制、配置保存 | 可重新打开项目并继续拍摄 | 1–2 周 |
| P3：短视频 | 时间轴、逐帧导出、编码、失败恢复 | 一条完整的 5–10 秒短片 | 1–2 周 |
| P4：持续扩展 | 更多车型、雨夜、开门、行驶、批量出片 | 按质量逐项增加 | 持续迭代 |

### 10.1 P0 是首要关卡

样片不满意时，优先解决模型、材质和美术问题，不急着扩展功能。必要时更换资产或调整最终渲染路线。

### 10.2 验收标准

| 维度 | 标准 |
|---|---|
| 视觉质量 | 近景无明显曲面破损、玻璃错误、悬浮轮胎或材质丢失 |
| 图片输出 | 先稳定验证 1080p，再验证 4K；不把高分辨率等同于高画质 |
| 实时预览 | 在当前电脑上以 1080p、约 30 fps 为目标，实测后确定档位 |
| 视频输出 | 帧数和时长正确，无漏帧、明显闪烁或突然跳变 |
| 可复现性 | 保存后重新加载，机位、车辆状态和场景配置保持一致 |
| 资源管理 | 切换车型能释放资源，长期操作不持续累积无用 GPU 资源 |
| 失败处理 | 缺失资产、显存不足、磁盘不足和导出失败都有明确提示 |

### 10.3 测试方式

- 固定几张标准机位，每次调整材质或升级渲染器后进行视觉对比。
- 测试配置保存与读取、固定时间动画求值、输出帧数和文件完整性。
- 在目标电脑的真实浏览器中验证，而不只依赖构建成功或无界面测试结果。
- 本地网页验证优先按项目约定使用 Chrome DevTools MCP：先列出页面，再创建本任务独立页面，以返回的页面 ID 操作。
- 用页面快照验证结构，用实际截图验证视觉；不能把工具连接成功等同于页面渲染正确。

## 十一、主要风险与应对

| 风险 | 应对方式 |
|---|---|
| 模型本身不准确 | 先看多角度参考与结构，在 P0 阶段验收，不靠后处理掩盖 |
| 模型授权不适配 | 采购前区分本地使用、成片用途及公开网页分发 |
| 实时与最终渲染不兼容 | 先建立材质和效果支持清单，再扩展高级效果 |
| 6GB 显存不足 | 限制场景规模，按需加载高精度资源，及时释放资源 |
| 视频渲染过慢或闪烁 | 先做短片、小样，测量后选择渲染档位与路线 |
| 视频帧占满磁盘 | 导出前估算空间，限制任务规模，提供可控清理 |
| 功能越做越多、迟迟不能出片 | 以具体作品验收每个阶段，而不是只统计功能数量 |
