# BMW G20 相机复核第一轮

日期：2026-10-03。起点：`de6d7a1`。本轮完成数值多解复核、候选比较功能和原图浏览器验证；**相机视觉关仍待审阅，未开始车头曲面**。

## 1. 结论先行

- A / B 前角机位可以保留为当前研究基线，未发现本轮求解方法返回的另一类低位姿态；这不证明解唯一或相机准确。
- C 近侧机位不能按原先的“低残差初值”直接冻结。加入 AP3P 返回分支后，发现相机前后位置不同的低机位候选；重复选点还会让求解结果越出高度先验。
- 原图读取及叠加已经可以正常完成。**当前限制是对应点与近似骨架的约束不足，不是浏览器或文件权限。**
- 不据此推断整个项目一定失败。四点相机问题没有稳定解，与公开图片是否足以指导一个展示级车头，是两个不同问题；但不能继续把这个机位当作可靠三维测量。

## 2. 本轮做了什么

1. 新增 `scripts/bmw_camera_review.py`：对三张开发图运行 SQPnP / EPnP；四点时再枚举 AP3P 的全部返回分支，每个分支用 LM 细化。不是穷尽全部数学解，重复收敛也不算独立证据。
2. 焦距系数固定为 `0.85 / 1.0 / 1.15`，分别使用原标注和已有重复标注；不添加、删掉或移动拟合点。
3. 保留每个候选的位姿、投影、逐点残差及拒绝原因；包括误差更小却不满足先验的候选，避免只展示“好看”的结果。
4. 在 EXIF 系数 1.0、原标注、满足当前先验的返回解中选择最低 RMS，**只作为审阅候选**。A / B 不增加重复按钮，C 新增独立候选文件。
5. 工作台新增 C 的“原基线 / 近侧 EXIF 低机位候选”切换、识别与风险说明。切换整个位姿及视场角，保持原图、骨架和其他机位不变，自动锁定；支持原有保存、导入导出和恢复机制。

未改：`skeleton.json`、`landmarks.json`、`cameras.json`、`config-lock.json`。报告记录前三个数值输入的 SHA-256（UTF-8、换行统一为 LF）；测试检查其未漂移。4 张留出图未读取或参与本轮拟合。

### 先验不是事实

焦距像素值采用 `imageWidth × EXIF毫米焦距 / 36 × 系数`，假设图宽对应 36 mm 传感器宽；主点取图像中心，畸变取零，保留全图裁剪。照片是否经过后期裁剪仍未知，不能把系数 1.0 称为实测内参。

相机须在正确车身侧、所有固定点深度在 `(0.05, 200)` m、高度在 `(0.1, 4)` m。这是本次研究范围，不是对真实摄影参数的证明；放宽高度阈值也不能自动让某个解可信。

实现参考：[OpenCV PnP 与多解接口说明](https://docs.opencv.org/4.13.0/d5/d1f/calib3d_solvePnP.html)。本机实际数值版本为 OpenCV 4.12.0 / NumPy 2.2.6，无新增安装。

## 3. 数值结果

固定点 RMS 是原始 4961 px 宽照片上的拟合内残差，**不是还原率或表面精度**。

| 机位 | 固定对应点 | 本轮处理 | 原标注 RMS |
|---|---:|---|---:|
| A · P90549627 | 6 | 保留原基线，EXIF 系数 1.0 | 36.16 px |
| B · P90549630 | 6 | 保留原基线，EXIF 系数 1.0 | 27.19 px |
| C · P90549635 | 4 | 原基线，系数 0.85 | 17.21 px |
| C · 同一张图 | 同样 4 点 | 新增 EXIF 系数 1.0 的低机位候选 | 22.37 px |

### C 的两组对照

| 参数 | 原基线 | 新候选 |
|---|---:|---:|
| X / m | +1.8436 | −0.3920 |
| Y / m | 0.2765 | 0.4755 |
| Z / m | 10.4124 | 12.6454 |
| 垂直视场角 | 30.3757° | 25.9867° |

原点为轴距中点地面，−X 指向车头。两组解把相机放在轴距中点的后方 / 前方，不能把 RMS 较小等同于真实观察方向。

不仅是焦距不同：**在同一个 0.85 焦距系数下**，AP3P 还返回 X = −0.6129 m、Y = 0.4915 m、Z = 10.8725 m 的低位候选，RMS 23.78 px。完整候选均保存在 [机器报告](camera-review-round1.json)，页面只显示两个代表性对照，未声称只有两解。

### 重复选点敏感性

- A：在相同 EXIF 先验下，换成重复标注后，相机位置变化约 0.030 m，RMS 37.54 px。
- B：相同设置下，位置变化约 0.082 m，RMS 25.37 px。
- C：四个点的重复偏移为 0、3.61、13.93、2 px。使用相同求解方法和三档焦距后，本轮返回解没有一个满足上述高度先验。出现了约 6.47–8.35 m 的高位解，也出现了接近或低于地面的分支。

这是“当前求解方案对现有对应点敏感”的实测，不是“物理上不存在相机”的证明。重复标注来自同一审阅者，不能当作统计置信区间或独立实验。

## 4. 真实图片叠加观察

通过原图文件选择控件读取三张官方 JPG，页面按原尺寸及 SHA-256 校验；未把照片公开到 HTTP 静态目录。实际保存截图并逐张打开查看。

- A / B：轮心、风挡角点附近可对照；机盖前缘、前端体块仍明显粗略，轮胎与车身外轮廓并非完全贴合。保留工作相机不等于接受这些骨架形状。
- C 原基线：四个标注附近相对接近，但车尾端面及车顶后部仍有偏差。
- C 替代相机：仍靠近四个标注，未参与拟合的车顶后段、后窗和车尾投影有所变化；没有形成足以确认“替代相机正确”的一致改善。
- 骨架未做遮挡剔除，远侧轮圈会透出。不能把透出的圆当作实车轮位，也不能凭稀疏线框评价精细车头还原度。

结论：本轮没有可靠依据自动提升 C 候选或签收完整相机关，主基线不变。

## 6. 如何复现

浏览器运行只依赖现有 Node / Three.js 工程。数值报告重新生成才需要上述 Python 依赖：

```powershell
python -X utf8 -m unittest discover -s scripts -p test_bmw_camera_review.py
python -X utf8 scripts/bmw_camera_review.py
npm test
npm run build
```

报告生成只覆盖 `camera-review-round1.json` 和 `camera-alternatives.json`，不覆盖正式相机、骨架或标注。不同 OpenCV 版本的收敛或分支顺序可能变化，重新生成后要审阅 diff，不能自动提升候选。

手动审阅：打开 `/#bmw` → 近左侧 / 相机 C → 选择 `P90549635.jpg` 原图 → 保持叠加模式 → 在相机参数区切换两个按钮。相机仍为候选，不是定稿。

## 7. 下一步决策，不继续盲目调参

本轮停止增加求解器和工具功能，不重复用同样四点无限压低误差。需要审阅的选择是：

1. 严格保留三机位冻结要求：先补能约束 C 观察方向和深度的可靠对应依据；仅增加没有可信三维位置的轮廓点不算解决。
2. 若目标优先是展示级可行性、而非相机恢复：由用户明确同意缩小关卡，A / B 作为临时工作机位，C 暂降为定性参考，做一块“机盖—灯角—翼子板”白模小样，以跨角度视觉结果决定继续或止损。不能称它为通过了原三机位相机关，也不能随即扩大到整车。

倾向第二条，避免把全部时间耗在不充分的四点标定上；**本轮只提出范围调整，不自行更改批准边界或启动曲面**。
